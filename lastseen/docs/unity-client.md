# Unity client

The wearer app: a Unity 6 (`6000.0.84f1`) Android app for the XREAL Beam Pro, with the XREAL One glasses mirroring the phone screen as the HUD.
It talks to the Worker over HTTP ([ARCHITECTURE.md](ARCHITECTURE.md), "HTTP API"). Nothing here has run on a device yet; what *has* run is listed under
"Verified".

## What is where

| Folder (repo root `Assets/Scripts/...`) | Contents |
| --- | --- |
| `Lastseen/` (assembly `Lastseen`, pure C#, unit-tested) | `Geo` (bearing, arrow angle, dead-reckoning step, pinhole position: ported from `packages/shared/src/geometry.ts`), `StepDetector`, `ObjectStabilityTracker` ("held still for N s"), `PoseRing`, `Payloads` (request bodies), `Replies` (response parsing), `WavEncoder` / `WavDecoder`, `ImageHash`, `LastseenConfig` |
| `LastseenApp/` (MonoBehaviours) | `LastseenController` (spawns itself at startup; buttons and status), `DeadReckoningTracker`, `LiveDetector`, `PlacementCapture`, `VoiceQuery`, `HudArrow`, `WorkerClient` |
| `DualCameraCapture.cs`, `Depth/` (teammates) | Camera2 dual-camera photo; the older locate-one-object flow (`TargetLocator`, `DepthLocator`; its tests still run) |
| `../Forgetmenot/` (teammates) | AR Foundation + MediaPipe bridge (`AndroidMediaPipeDetector`) |

Removed: `FindObjectController`, `VoiceCommand`, `VoiceCommandResponse`. They drove the one-shot "find it now" flow through `cloudflare/locator`'s
`/command`; `POST /api/query` replaces `/command`, and `POST /api/ingest` (stereo) replaces the locator's `POST /`. `cloudflare/locator` is kept for reference only and
should not be deployed.

## Setup

1. **Worker**: `pnpm run deploy` from `lastseen/` (needs the secrets from the README: `DEVICE_TOKEN`, and `OMNI_API_KEY` once you have one). Until then the Worker runs
   the mock (`MOCK_OMNI=1`): the whole path works, the answers are canned.
2. **Client config**: copy `Assets/Resources/lastseen.example.json` to `Assets/Resources/lastseen.json` (git-ignored) and fill in `workerUrl`, `token`, `deviceId`.
   The token is baked into the APK: fine for your own debug build, not for distribution. With no file the app shows `CONFIG: ...` on screen and does nothing else.
3. **MediaPipe model**: `python forgetmenot_cv/download_model.py --android` (see `Assets/Forgetmenot/README.md`).
4. **Scene**: for automatic logging the scene needs an AR camera (`ARCameraManager`, from the XR Origin). `LastseenController` finds it and adds `LiveDetector` itself. Without one the
   app still works through the "Log what's in front of me" button and push-to-talk.
5. **Player settings**: *Active Input Handling* is already "Input System Package (New)", which the dead reckoning relies on (the legacy `Input.*` API would throw).
   If the app reports `no connection` although the network is fine, set *Other Settings -> Internet Access* to *Require*.
6. Build for Android and install. The manifest already has camera and microphone.

## Verified

- `pnpm unity:test`: compiles every script (including the `Assembly-CSharp` glue against AR Foundation, Input System and the Forgetmenot bridge) in a headless Unity and runs the
  EditMode tests: 65 pass. They cover the geometry against `packages/shared/test-vectors/geometry.json` (generated by the TypeScript, so C# and TS cannot drift), the step detector
  on the same 30 Hz accelerometer stream (same 36 steps at the same timestamps as the TypeScript), the stability tracker (holds, moves, walking, gaps, refresh), request bodies (optional
  fields absent, never `0` or `""`), reply parsing, WAV encode/decode, the image hash and the config. The teammates' `Depth` tests run too.
  If the project is open in an editor the script tests a scratch copy (Unity will not open one project twice).
- `pnpm unity:test -- --android-branches`: additionally compiles the `#if UNITY_ANDROID && !UNITY_EDITOR` code (`DualCameraCapture`, the microphone permission, the JNI detector),
  which the editor skips. Compile check only.
- The Worker side of the same requests: `pnpm sim:local` posts a real stereo pair to `/api/ingest`, asks through `/api/query`, and reads `/api/memory`, against `wrangler dev`.

## Not verified (nothing has run on a Beam Pro)

Everything that needs the device: the sensors, the camera pipeline, MediaPipe, the microphone, playback, the glasses. The checks below are ordered so each one isolates a single unknown.

## First on-device checks

1. **Pose line** (top of the screen): `pose x, y m  heading °  steps N  still|walking`. Walk 10 m in a straight line: `steps` counts up and `y` (facing the way you started) is
   about the distance. Step length is a guess (0.7 m): set `stepLengthM` in `lastseen.json` to `10 / steps`.
2. **Heading direction**: turn right on the spot. The heading must **increase**. If it decreases, set `invertHeading` on `DeadReckoningTracker`; if it is wildly off (jumps, or does
   not follow the turn), flip `convertAttitude`. (The Input System documents its `AttitudeSensor` as the same as `Gyroscope.attitude`, which needs the usual conversion; this is the
   one place a wrong assumption would show up as a wrong direction, not a crash.) With no attitude sensor the heading falls back to the AR camera yaw.
3. **Log now**: press *Log what's in front of me* with an everyday object on a table. The status goes `taking photo...` -> `sending N KB, M objects seen...` -> `logged keys at 1.4, 2.0 m,
   -0.2 m vs camera [stereo]`.
   - `[omni]` instead of `[stereo]`: the depth match failed; `GET /api/memory` (the `traces` list) has a `stereo` entry with the reason (`ambiguous`, `too_far`, `out_of_image`, ...).
   - The photo never arrives: the dual camera failed (see the DualCam status in `adb logcat -s Unity`). Run the hardware probe (`pnpm android:probe`): its camera and concurrent-camera sections say
     whether two cameras can be open at once.
   - If the baseline of the two cameras is *vertical* in the saved photo (the photo is rotated by `rotationDegrees = 90`), block matching along x finds nothing: `no_match` / `ambiguous` on every object.
4. **Calibrate the stereo numbers**: put a flat, textured object at exactly 1.0 m and again at 2.0 m and read the depth off the trace. The depth is `fx * baseline / disparity`, so a constant factor
   error is the baseline (`baselineM`) or the field of view (`hfovDeg`, measure it in the probe report, section 3). Set both in `lastseen.json`; a swapped left/right shows as `no_match` (set `stereoSwap`).
5. **Automatic logging**: `detector N frames` on screen must count up. Put an object down and stand still: about 4 s later it logs by itself. Walking, or the object still being handled, never logs.
   If `N` stops counting after a photo, or the photo fails while the AR camera runs, the two camera users are colliding: that is exactly what the probe's exclusivity section measures. Fallback:
   remove `LiveDetector` and use the button (or, later, the voice narration trigger).
6. **Ask**: press *Talk*, say "where are my keys", press *Stop*. Expect the status `asking...`, a spoken answer, and the orange arrow under your line of sight, with the object's name, distance and age.
   The arrow turns green within 12 degrees of straight ahead. *Recenter* (look straight ahead, then press it) re-aligns the glasses' yaw with the chest heading; the first target does it automatically.
7. **Cost check** before a long session: `GET /api/memory` shows `budget`; with `MOCK_OMNI=0` every ingest is 2 vision calls and every question 1-2.

## Known limitations

- **Session origin**: the position resets to (0, 0) when the app starts, but the Worker's memory persists (24 h). Objects logged in an earlier session are not comparable to the current
  position. Use "forget everything" (or a new `deviceId`) between sessions until there are zone anchors (`pose_correction` exists on the wire, and nothing sends it yet).
- **Drift**: steps drift by a few percent of distance walked, and heading by whatever the OS fusion does indoors near metal. Confidence decays with steps and time
  (`exp(-steps/120) * exp(-t/600)`); below 0.35 the HUD shows words ("near the desk") instead of an arrow.
- **Chest, not head**: the camera and the dead reckoning are on the chest; only the arrow uses the glasses' yaw. A 6DoF head pose from the XREAL SDK would not help position the chest camera.
- **`verify_visible` over HTTP** needs a `frame` in the query body; the client does not send one yet, so "is it still there?" reports "inconclusive".
- **No echo cancellation** for barge-in: talking over the assistant stops playback, but it does not tell the Worker to cancel the turn.
- **Stereo assumes** the two cameras are level and the baseline is along image x; depth is measured on the box centre only.
